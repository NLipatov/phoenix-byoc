# Named LLM authoring contract v1 (Agents-owned portion)

`values.schema.json` is the canonical structural source for optional `llm` and `agentInputDelivery` authoring. Merge its root `properties`, root `allOf`, and `llmConnectionsV1_` definitions into the installed chart's existing root schema; do **not** replace its retention/other constraints. The complete authoring envelope (including generic-only inputs) is the entry point; the definition refs are local and namespaced. Existing profiles/modelIds provide model targets and trusted catalog association, not a new authoring field. The three-connection draft seed in `docs/superpowers/specs/assets/` is not a released artifact and is unchanged.

The structural name grammar, every fixed reservation/prefix, per-map limits and enterprise UUID pattern/count are derived from the imported Engine `contract.json` by the offline exporter. `--check` fails when the checked-in schema/manifest differs from that derivation. Plain destinations and platform references reject fixed reservations, reserved prefixes and customer `PHOENIX_LLM_*`; secret destinations additionally reject Engine's secret-only prefixes. Do not apply secret-only exclusions to plain/platform reference names: explicit platform slots remain authorizable. Kubernetes Secret references in both maps use DNS-subdomain names (253 characters maximum; lowercase alphanumeric label edges, with internal hyphens and dots between nonempty labels, no additional per-label 63-character limit) and nonempty Kubernetes Secret keys (253 characters maximum; letters, digits, `-`, `_`, `.`, excluding `.` and names starting with `..`). Secret-reference syntax uses standard JSON Schema constraints and RE2-compatible patterns for Helm/gojsonschema as well as Ajv (no lookahead). These source/API semantics follow implementation knowledge; no pinned Kubernetes validator source or live API verification was available offline. Referenced Secrets and keys must still exist and be authorized by the producer.

`semantic-rules.json` is the data-only v1 supplement to the structural schema: export derives its status, forbidden-name, native platform-key, protected-header and C0/DEL/C1 inventories from the same pure constants used by the owner validators. These rules do not form a provider registry or a new semantic executor. A capability gate admits only `offline-proven`, with exactly one matching route/API/authMode candidate (`API` omission still requires one candidate for route/authMode); `blocked`, unknown statuses and duplicate/absent tuples fail. The shipped manifest remains all `blocked`. The seven listed native platform keys require a platform declaration; other native keys require plain input. API keys require `secretEnv`, while a header reference resolves from exactly one declared plain, secret or platform destination, including an already-used platform destination. Reject cross-source collisions even when values compare equal; do not treat ordinary env as platform provenance. Chart/BYOC know declarations, not Secret bytes or actual runtime workload identity.

Connection names and JSON header/native member names additionally exclude only `__proto__`, `constructor`, and `prototype`; these exclusions do not broaden Engine's destination reservations. Referenced **known** plain values, literal/resolved headers and URLs reject C0 U+0000–U+001F plus DEL/C1 U+007F–U+009F. Headers also require unique case-insensitive token names and reject protected names, nonempty literal dollar/command forms and more than 65536 UTF-8 bytes. URLs require HTTPS with a hostname and no userinfo/query/fragment. Generic known plain values follow the imported Engine `env.values` rule: reject NUL, **allow empty strings and unrelated permitted controls**. Do not inspect opaque Secret contents at authoring time. Authoring structural/semantic acceptance is separate from runtime capability and platform identity proof.

The original 74 `semantic-vectors.json` **VALUES** cases remain unchanged. `authoring-vectors.json` adds 18 distinct synthetic VALUES cases (16 named + two generic-only) with explicit `applicability` for connection validation, flat-env decoder, or Engine/full-envelope admission. `capability-vectors.json` separately adds five synthetic manifest cases for exactly-one tuple/status predicates and never modifies the shipped manifest. `semantic-vectors.json` separates structural acceptance from semantic admission (e.g. source collisions and header case duplicates). `transport-vectors.json` records flat-env and synthetic generic delivery examples. Its delivery example uses the amended two-field policy (`version`, `allowedEnterpriseIds`) and no image input; it does not certify Engine runtime behavior. A structural pass is never native authorization: every `capabilities.json` route/API/auth variant remains `blocked`, with no pinned native proof or live acceptance. Tests of schema-positive vectors are not native wire tests.

**Producer import:** The Engine-owned `contracts/agent-input-delivery/v1/{contract.json,fixtures.json,manifest.json,README.md}` is imported byte-identically from supplier commit `5f0bbdfb3b54b76505c85e6733e3b01b3db7dba0`. Its manifest hashes identify exact member bytes; `sourceRevision` `211274896e861d392c560ccb346078c5acc58087` is the pre-export source lineage, not the export commit or an image attestation. Runtime validation uses the imported reserved-name inventory. This source-level import does **not** prove delivery wiring, native runtime support, image eligibility or cross-repo deployment compatibility. `PHOENIX_LLM_*` remains rejected in generic customer env/secretEnv; generated named env is a separate transport output. Chart/BYOC must check same-kind `llm.secretEnv`/generic `secretEnv` overlap (and same-kind plain origins) before combining maps; resolved runtime `ConnectionSources` cannot reconstruct that provenance. Chart/BYOC and runtime admission must also reject plain/secret/platform cross-map overlaps, including equal values; enforce the flattened generated plain/secret destination counts and cross-map union limits before delivery. JSON Schema's per-map `maxProperties` does not enforce flattened totals. Check total UTF-8 **bytes**, including selected-file/aggregate bounds from Engine, not character `maxLength`; validate source existence, platform allowlist, secret provenance, header case collisions and reference kinds. Structural-only vectors are not admission evidence; semantic-negative vectors must remain fail-closed downstream. Legacy credential delivery remains separate and unchanged; named-v1 subscription/OAuth/login/refresh fields are rejected.

`npm run contracts:llm:check` checks checked-in manifest and members without writing. `npm run contracts:llm:export -- --out artifacts/llm-connections-v1` writes the same deterministic members at the chosen output root (including this README), without claiming Engine files. The manifest `sourceRevision` is a content revision of these Agents-owned members, **not** a Git revision, image identity or production attestation. Consumers must pin checksums and release evidence separately. Built runtime assets are copied under `dist/contracts/llm-connections/v1/`; resolve them package-relative, never relative to the process working directory.
